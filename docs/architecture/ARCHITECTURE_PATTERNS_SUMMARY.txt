    ARCHITECTURE PATTERNS SUMMARY: Parser Usage Analysis
═══════════════════════════════════════════════════════════════════════

QUESTION: Is it inconsistent to use parsers for some services but not 
          for blockchain providers?

ANSWER: NO - This is GOOD PRACTICE showing appropriate pattern selection
        based on data source characteristics.

───────────────────────────────────────────────────────────────────────
PATTERN 1: EXCHANGE/BROKER (Binance, IBKR)
───────────────────────────────────────────────────────────────────────

Flow: Service → CRUD → Parser → Database

    binancecom_service.py          crud_binancecom.py           binancecom_parser.py
    ┌──────────────┐              ┌──────────────┐             ┌───────────────┐
    │ • API auth   │──raw data──→ │ • Ingestion  │──raw data──→│ • Transform   │
    │ • Fetch data │              │ • Counting   │             │ • Map fields  │
    │ • Orchestrate│              │ • Error mgmt │             │ • Config rules│
    └──────────────┘              └──────────────┘             └───────────────┘
                                                                       │
                                                                       ↓
                                                              Transaction dict[]

WHY SEPARATE PARSER?
✓ Complex API response formats
✓ Configuration-driven business logic (symbol → portfolio mapping)
✓ String to Decimal conversions
✓ Multiple transactions per API record (FX trades)
✓ High reusability across different ingestion scenarios
✓ Easy to test independently

───────────────────────────────────────────────────────────────────────
PATTERN 2: BLOCKCHAIN PROVIDERS (BTC, ETH, SOL, etc.)
───────────────────────────────────────────────────────────────────────

Flow: Service → Provider (embedded normalization) → CRUD → Database

    crypto_wallet_service.py       btc_provider.py
    ┌──────────────┐              ┌────────────────────────────────┐
    │ • Orchestrate│──call API──→ │ • API failover (multiple srcs) │
    │ • Enrich:    │              │ • Caching (TTL)                │
    │   - wallet_id│              │ • _normalize_transaction()     │
    │   - port_id  │              │   ├─ Parse formats             │
    │   - acct_id  │              │   ├─ UTXO analysis             │
    │ • Category   │              │   ├─ Net calculations          │
    └──────────────┘              │   └─ Return Transaction dict[] │
                                  └────────────────────────────────┘

WHY NO SEPARATE PARSER?
✓ Each blockchain has different transaction models:
  - Bitcoin: UTXO (inputs/outputs analysis)
  - Ethereum: Account model (from/to addresses)
  - Solana: Complex programs and instructions
✓ API failover requires format awareness
✓ Tight coupling between fetch and parse logic
✓ Caching happens at provider level
✓ Provider IS a "parser + client" hybrid
✓ Splitting would break cohesion

───────────────────────────────────────────────────────────────────────
COMPARISON TABLE
───────────────────────────────────────────────────────────────────────

Aspect                 │ Exchange/Broker    │ Blockchain
───────────────────────┼────────────────────┼─────────────────────────
Data Source            │ REST API           │ Multiple blockchain APIs
Response Format        │ Consistent JSON    │ Varies by provider/chain
Transformation Logic   │ Config-driven      │ Protocol-specific
API Failover           │ Single source      │ Multiple sources
Caching Location       │ Service-level      │ Provider-level (TTL)
Business Logic         │ Portfolio mapping  │ UTXO/account analysis
Parser Location        │ Separate file      │ Embedded in provider
Reusability            │ High               │ Provider-specific
Testing Strategy       │ Parser separate    │ Provider as unit

───────────────────────────────────────────────────────────────────────
SOLID PRINCIPLES SATISFIED
───────────────────────────────────────────────────────────────────────

✓ Single Responsibility
  - Each component has one clear purpose
  - Separation matches natural boundaries

✓ Open/Closed
  - Easy to add new exchanges (new service/crud/parser)
  - Easy to add new blockchains (new provider)

✓ Liskov Substitution
  - All providers follow same interface
  - All parsers return Transaction dict[]

✓ Interface Segregation
  - Clients depend only on what they need
  - No forced dependencies

✓ Dependency Inversion
  - CRUD depends on abstractions (parser interface)
  - Service depends on provider map
